TOP 10 · Developer tools & agents · Datadog Systems Research · MIT

Datadog open-sources Ephyra, an agentic property-based tester finding 70+ SQLite bugs

Datadog Systems Research released MIT-licensed ephyra (v0.0.1 Rust library plus ephyra-cli), combining property-based testing with inductive hill-climbing where coding agents rewrite test-case generators from code-coverage feedback rather than mutating individual inputs. Ephyra runs surfaced 70+ bugs in SQLite, 20 in PostgreSQL, and 25 in Lean, while its autonomous agent found defects in FoundationDB, TigerBeetle, OCaml, LiteLLM, FastMCP, and Bun; failures print a shrunk counterexample and an EPHYRA_REPLAY=<seed>:<iteration> line that reruns that exact case, with failing cases remembered in .ephyra/regressions/ so the next run tries them first.

Builder move: Install ephyra-cli and point a coding agent at README.md and STARTUP.md on one parser, state machine, or storage invariant to turn fuzzing runs into repeatable regression tests.

Caveat: Almost all code in the repository is experimental and subject to change (ephyra is at v0.0.1); case-studies/sqlite/vendor/fetch.sh pulls SQLite trunk for the SQLite and Turso case studies, while turso/differential, turso/apidiff, and cedar/generator require separate target checkouts at the repo root.

TOP 10 · Security & policy · Nov 26 · MITRE CVE (Claude Security Scans, Sonar)

Apache Airflow CVE-2026-120353 exposes worker RCE across common.ai LLM and agent decorators

Apache disclosed CVE-2026-120353 affecting apache-airflow-providers-common-ai (v0.1.0 to <v1.2.0), standard (v0.3.0 to <v1.22.0), cncf-kubernetes (v10.5.0 to <v11.0.0), and common-sql (v1.32.0 to <v3.0.0), where TaskFlow decorators—including @task.llm, @task.agent, @task.llm_sql, @task.llm_branch, @task.llm_file_analysis, and @task.llm_schema_compare—rendered Jinja templates a second time on workers. Any attacker who can trigger a DAG run (run conf) or control text passed into an affected decorator's env, arguments, or prompt (such as a ticket or downloaded document) can execute arbitrary commands on the worker and read connection passwords and Airflow Variables.

Builder move: Upgrade apache-airflow-providers-common-ai to v1.2.0, standard to v1.22.0, cncf-kubernetes to v11.0.0, and common-sql to v3.0.0 or later immediately.

Caveat: Exploitation applies only to deployments using an affected decorator in a DAG that passes trigger run conf or attacker-controlled text through env, parameters, or prompts.

Claude Code v2.1.332 adds MCP server skills and load hooks alongside new /ship playbook

Claude Code v2.1.332 (Nov 25) adds beta skills from MCP servers (shown as server:skill in /), a PreSkillShellCommand hook event that can refuse a skill or command's inline shell commands as it loads, an OpenTelemetry assistant_response event, a 20-second timeout fixing hangs on locked named pipes (such as secrets-mounted .env files), and shortening of oversized hook logs past ~50,000 characters. Separately, Addy Osmani's Nov 24 claude.dev playbook walks non-admin GitHub developers through running /code-review (including high effort and --comment), /ship, and /steward locally in their own sessions.

Builder move: Upgrade to v2.1.332, configure a PreSkillShellCommand hook before enabling third-party MCP server skills, and run /code-review on your branch before pushing PRs.

Caveat: Settings files using that hook open a startup dialog on v2.1.331 and older, MCP server skills remain in beta, and automatic team-wide Claude Ship workflows require admin setup.

TOP 10 · Models & APIs · LlamaIndex · CPU & Wasm pipeline · ,

LlamaIndex releases 8.1M-parameter OCRia-nano-1 running layout and OCR on CPU and Wasm

Distilled from LlamaIndex's 4B OCRia-1 at 1/500th the parameters, OCRia-nano-1 pairs a line detector, script router (Latin, CJK, Arabic/Hebrew RTL, plus ~17 more scripts), four recognizers, and LayoutNet inside LiteParse (60–75 MB download with ONNX Runtime via lit models pull ocria-nano). It scores 59.2 on ParseBench-2—lifting LiteParse from 48.7 with Tesseract and beating CPU parsers Indra (55.1) and Marker (52.5)—at 27.8 pages/sec on 16 vCPUs (426 ms per page on one core, or about 1–4 s per scanned page on a laptop in single-threaded WebAssembly).

Builder move: Benchmark lit parse scan.pdf --format markdown on scanned multi-column and tabular PDFs where GPU VLM parsing is too expensive or browser/edge Wasm execution is needed.

Caveat: The custom OCRia-nano-1 license stays free for academic/non-profit research, teaching, evaluation, benchmarking, and non-production internal R&D, but requires a separate commercial license above $2M in annual revenue or $2M in total funding, and for any use inside a document-parsing, OCR, or extraction product competing with LlamaParse or LlamaCloud regardless of size.

TOP 10 · Infrastructure & economics · Nov 26 · v18-919794500-r367 · ,

llama-cpp-rdna-boosts lifts AMD R9700 prefill to 1,300 tok/s as practitioner flags routing hacks

Rebased onto llama.cpp commit 919794500, llama-cpp-rdna-boosts ships 19 default patches (18 official blocks 0000–0017 plus temporary block 0300) enabling default-on BF16 KV cache, WMMA Flash-Attention, fused MoE and k-quant decode, MTP decode, chunked gated-delta-net prefill, and qwen4exp support for AMD RDNA GPUs. In a Nov 26 devnull.land post testing an AMD R9700 eGPU on ukisai/Swift-1.5-Qwen3.8-27B-GGUF (Q6_K_L + MTP) via ghcr.io/stew675/llama-cpp-rdna-boosts:server-rocm-10.1, prefill rose from ~700 to ~1,300 tok/s (~1.86×) and generation from ~35 to ~55 tok/s, contrasting rdna-boosts's patchset (which the author notes is somewhat opaquely documented yet offers some transparency) against the author's report of Strata preferring VRAM-resident MoE experts over offloaded ones.

Builder move: Benchmark the rdna-boosts ROCm container on RDNA hardware and verify model accuracy before adopting speed-focused third-party inference forks.

Caveat: The patchset pins to a single upstream llama.cpp commit (919794500), includes a temporary 0300 MoE relaxation block marked for removal, and the devnull.land speedup measures one R9700 eGPU setup.

TOP 10 · Infrastructure & economics · Nov 26 · Agent Duel (OpenCode)

Agent Duel telemetry shows GPT-6.2 Astra and Sol cut reasoning and output tokens

Paired head-to-head real-work battles inside Agent Duel (built on OpenCode) plot spending relative to opponents against leaderboard Elo from GPT-6 to GPT-6.2, showing sharp drops in reasoning tokens (p = 0.00013 for Sol, p = 0.0064 for Astra) and output tokens (p = 0.0055 for Sol, p = 0.022 for Astra). Relative to predecessors Astra 6 and Sol 6.1, which sat near typical opponent token profiles, Astra 6.2 and Sol 6.2 become low-reasoning underthinking outliers.

Builder move: Measure per-task reasoning tokens and pass rates in your own harness before migrating multi-step agent workloads from GPT-6/Sol 6.1 to GPT-6.2.

Caveat: Measurements come from observational, opponent-relative battles inside one OpenCode-based arena rather than OpenAI's internal telemetry, and report relative opponent ratios rather than absolute token budgets.

OS-Omni live cross-platform CUA benchmark puts Claude Opus 5.5 8.8 points behind humans

OS-Omni v1 releases 300 final-state-evaluated tasks across 6 platforms (48 each on Windows, Ubuntu, macOS, iOS, Android, and Web) plus 12 hard single-screen desktop+Android (scrcpy) workflows, with human studies averaging 67.54 interaction steps across OS-Omni tasks versus 15.0 on OSWorld. Claude Opus 5.5 leads Macro-Avg at 68.5% (8.8 points below the 77.3% human average), ahead of GPT-6-Astra (66.1% Macro; 67.0% Micro, 201/300 vs. Opus's 200/300) and Gemini 4 Argon (58.6% Macro); all three beat humans on Linux yet best iOS (41.7%) and macOS (54.2%) scores lag humans by 33.5 and 25.6 points, while DeepSeek V4.1 Flash (30.4%) and Qwen 3.8 Max (13.1%) trail steeply.

Builder move: Benchmark computer-use agents per target operating system rather than assuming Linux scores transfer to macOS or iOS, and use OS-Omni v1's final-state evaluators for long-horizon regressions.

Caveat: Performance varies sharply by operating system, and the GitHub task release does not bundle VM snapshots, installed applications, or model credentials.

TOP 10 · Research & evaluation · Nov 25 · arXiv:2611.34051

Stable GDN-2 mitigates Gated DeltaNet-2 state blow-ups, lifting 128K RULER by 6.80 points

Researchers traced long-context training failures in Gated DeltaNet-2 (GDN-2) to asymmetry between reading and modification directions during erasure, producing non-normal erase operators whose directional gains can accumulate exponentially when amplified state directions align with subsequent expanding directions, even without new writes. Replacing that update in Stable GDN-2 with symmetric erasure (under standard key normalization and gate constraints) plus decay-regulated residual writing establishes an O(sqrt(T)) upper bound on recurrent state growth while retaining chunkwise parallel computation, lifting 128K average RULER by +6.80 points on 1.6B-parameter recurrent models (11.62 vs. 4.82) and boosting nine-task hybrid accuracy by +0.62 percentage points.

Builder move: Audit GDN-2 and related linear-attention training stacks for asymmetric erase operators before extending sequence lengths to 128K tokens.

Caveat: Reported experiments stop at 1.6B-parameter models, leaving training stability at frontier model scales untested.

TOP 10 · Security & policy · Nov 23 · 12,384 trials · MIT harness · ,

12,384-trial database agent audit shows engine undo controls surviving damage

A preregistered two-layer study scripted 22 canonical database mistakes across four relational engines under five permission and two recovery arms (792 cells, 874 recovery drills), then ran 12,384 live tool-calling agent trials (9,468 across PostgreSQL, MySQL, SQLite, ClickHouse, Cassandra, MongoDB, Valkey, Kafka, and OpenSearch plus 2,916 on MariaDB, Redis, and Elasticsearch) archived on Zenodo. Scoring loss that survives each engine's native undo drill finds engines differ less in what a mistake destroys than in what they let operators undo; only 3/7 preregistered hypotheses met their decision rule, and H4 (whether attempted damage varies more across engines than across models) met its rule under the preregistered measure but not once requested writes were excluded.

Builder move: Test engine-native undo and recovery drills and enforce least-privilege database roles before granting agents write access rather than relying on prompt rules alone.

Caveat: Layer B evaluated six small locally served open-weight models (4B to 12B parameters plus a 35B MoE with ~3B active) rather than frontier models, and four of seven preregistered hypotheses did not meet their decision rule.

TOP 10 · Builder behavior · Nov 24 · AI Engineer (48.8K+ views)

Jarred Sumner details shipping Bun's multi-million-line agent-written AOT compiler cutting memory 4x

Bun creator Jarred Sumner (Anthropic) detailed merging a PR of several million agent-written lines adding an ahead-of-time compiler to Bun—the runtime behind Claude Code—after five rewrites in about a month, alongside a walkthrough of what he does all day with 140 agents at once. Choosing to make JavaScript faster instead of rewriting Claude Code in Rust cut memory use by ~4× and sped startup ~2×, using tests that predate the project to keep agent-written compiler code trustworthy.

Builder move: Anchor large agent-written rewrites to test suites that predate the refactor and plan for multiple rewrites rather than patching a weak first pass.

Caveat: Claims are drawn from Sumner's conference talk metadata, which links only his X profile and bun.sh without a public benchmark harness or standalone AOT PR diff.
